## Nazariy savollar

### 1. OOP ning 4 ta asosiy ustunini (pillar) ayting va har birini JS misolida tushuntiring [Junior+]

<details>
<summary><strong>Javob</strong></summary>

OOP 4 ta ustun (pillar) ga qurilgan:

1. **Encapsulation** — ma'lumotni yashirish va himoyalash
2. **Abstraction** — murakkablikni yashirish, faqat kerakli qismini ko'rsatish
3. **Inheritance** — bir class'dan boshqasiga meros olish (code reuse)
4. **Polymorphism** — bir xil nomli method turli class'larda turli xil ishlashi

```javascript
// 1. Encapsulation — private field bilan himoya:
class BankAccount {
  #balance = 0;
  deposit(amount) {
    if (amount > 0) this.#balance += amount;
  }
  get balance() { return this.#balance; }
}

// 2. Abstraction — foydalanuvchi faqat play() ni biladi, ichki dekoder mexanizmi yashirin:
class AudioDecoder {
  decode(file) { /* ... murakkab decoding logic ... */ return "decoded audio"; }
}
class MediaPlayer {
  #decoder = new AudioDecoder();
  play(file) { return this.#decoder.decode(file); }
  // Foydalanuvchi #decoder, decode() haqida bilmasligi kerak — faqat play()
}

// 3. Inheritance — meros:
class Animal {
  speak() { return "..."; }
}
class Dog extends Animal {
  speak() { return "Hav!"; }
}

// 4. Polymorphism — turli xil xatti-harakat:
const animals = [new Animal(), new Dog()];
animals.forEach(a => console.log(a.speak()));
// "..." , "Hav!" — bir xil method, turli natija
```

### Edge Cases
- **JS'da `abstract` keyword yo'q** — Abstraction faqat private fields, `new.target` check, va konvensiya orqali emulatsiya qilinadi
- **Multiple inheritance yo'q** — `extends` faqat bitta class'dan; mixin pattern (factory function) orqali multiple capability qo'shiladi
- **Encapsulation `_` prefix bilan** — bu faqat konvensiya, hech qanday himoya yo'q; `#privateField` til darajasida enforce qilinadi

### Follow-up savollar
1. **"OOP printsiplari interview'da qaysi tartibda muhim?"** — Encapsulation va Polymorphism kunlik kod uchun eng muhim; Inheritance hozir composition'ga ustunlik bermoqda; Abstraction architectural printsip
2. **"Bularning hammasi class'siz mumkinmi?"** — Ha, factory function + closure orqali to'rttasi ham implement qilinadi (encapsulation closure, polymorphism duck typing, va h.k.)

</details>

### 2. Encapsulation nima va JS da qanday qilinadi? [Junior+]

<details>
<summary><strong>Javob</strong></summary>

Encapsulation — ob'ektning ichki state'ini tashqi koddan **berkitish** va faqat belgilangan method'lar orqali kirish imkonini berish.

JS da encapsulation qilishning asosiy usullari:

```javascript
// 1. Private fields # (zamonaviy, eng yaxshi usul):
class User {
  #password;
  constructor(name, pass) {
    this.name = name;
    this.#password = pass;
  }
  checkPassword(pass) { return pass === this.#password; }
}
const u = new User("Ali", "secret");
// u.#password; // ❌ SyntaxError — tashqi kirish taqiq

// 2. Closures (ES6 dan oldingi pattern):
function createCounter() {
  let count = 0; // private — tashqaridan ko'rinmaydi
  return {
    increment() { count++; },
    getCount() { return count; }
  };
}

// 3. WeakMap:
const _data = new WeakMap();
class Wallet {
  constructor(balance) { _data.set(this, { balance }); }
  getBalance() { return _data.get(this).balance; }
}
```

**Muhim:** `_` prefix (underscore convention) encapsulation **emas** — bu faqat kelishuv, hech qanday himoya bermaydi. `#` private fields esa til darajasidagi enforcement.

### Edge Cases
- **`#field` tashqi access** — agar tashqaridan `instance.#field` chaqirilsa — `SyntaxError` (runtime emas, parse-time)
- **`Reflect.get` `#field` o'qiy olmaydi** — private fields metaprogramming API'ga ko'rinmaydi
- **WeakMap encapsulation pre-ES2022** — production code'da hali ham keng ishlatiladi (eski browser support); `#` ga migration TC39 stage 4 dan keyin standart bo'ldi

### Follow-up savollar
1. **"`#field` va `WeakMap` farqi nima?"** — `#field` faster (V8 direct slot access), syntactically clean; `WeakMap` more flexible (cross-class access, debugging easier)
2. **"Private static method bormi?"** — Ha, `static #methodName()` — class darajasida private (faqat shu class internal'da ishlatiladi)

</details>

### 3. Abstraction va Encapsulation farqi nima? [Middle]

<details>
<summary><strong>Javob</strong></summary>

Ko'pchilik bu ikkisini aralashtirib yuboradi. Farqi:

| | **Encapsulation** | **Abstraction** |
|---|---|---|
| **Maqsad** | Ma'lumotni **himoyalash** | Murakkablikni **yashirish** |
| **Savol** | "Kim kirishi mumkin?" | "Nimani ko'rsatish kerak?" |
| **Vosita** | Private fields, closures | Public API, facade |
| **Yo'nalish** | Ichki state ni berkitish | Tashqi interface ni soddalashtirish |

```javascript
class Car {
  // Encapsulation — ichki state yashirin:
  #engine;
  #fuel = 100;

  constructor(engine) {
    this.#engine = engine;
  }

  // Abstraction — foydalanuvchi faqat shu method'larni biladi:
  start() {
    this.#checkFuel();       // murakkab ichki logika
    this.#engine.ignite();   // tashqi dependency
    this.#warmUp();          // ichki jarayon
    return "Mashina yurdi";  // sodda natija
  }

  // Ichki murakkablik — yashirin:
  #checkFuel() {
    if (this.#fuel <= 0) throw new Error("Yonilg'i yo'q");
  }

  #warmUp() {
    // 50 qatorlik murakkab logika...
  }
}

// Foydalanuvchi faqat start() ni biladi — ichki 3 ta qadam haqida bilmasligi kerak
// Bu ABSTRACTION
// #engine, #fuel ga kira olmasligi — bu ENCAPSULATION
```

### Edge Cases
- **Encapsulation'siz abstraction** — public field bilan ham sodda API berish mumkin, lekin ichki state oshkor (consumer'lar `instance.fuel = -100` qila olishadi — buzuq state)
- **Over-abstraction** — abstraction qatlami juda ko'p bo'lsa, kod tushunish qiyinlashadi (5 layer'lik facade — kim qaysi method'ni chaqiradi noaniq)
- **Leaky abstraction** — sodda interface ostida ichki murakkablik "sizib chiqadi" (masalan, `start()` error message'i ichki SQL syntax oshkor qilsa)

### Follow-up savollar
1. **"Abstraction class'siz mumkinmi?"** — Ha, function bilan: `processPayment(amount)` — ichki Stripe API, validation, retry — caller bilmaydi
2. **"Interface (TypeScript) abstraction'mi yoki encapsulation?"** — Abstraction — public API'ni belgilaydi, implementation oshkor qilmaydi

</details>

### 4. Polymorphism JS da qanday ishlaydi? Turlarini ayting. [Middle]

<details>
<summary><strong>Javob</strong></summary>

Polymorphism — "ko'p shakllilik". JS da 3 turi bor:

**1. Method Overriding** — child class parent method ni qayta yozadi:

```javascript
class Shape {
  area() { return 0; }
}

class Circle extends Shape {
  constructor(r) { super(); this.r = r; }
  area() { return Math.PI * this.r ** 2; } // override
}

class Square extends Shape {
  constructor(s) { super(); this.s = s; }
  area() { return this.s ** 2; } // override
}

// Polymorphism — bir xil method chaqiruv, turli natija:
[new Circle(5), new Square(3)].forEach(s => console.log(s.area()));
// 78.54, 9
```

**2. Duck Typing** — type emas, behavior tekshiriladi:

```javascript
// Bu ob'ektlar hech qanday umumiy class'dan meros olmagan
const file   = { read() { return "file content"; } };
const stream = { read() { return "stream data"; } };

function processInput(source) {
  return source.read(); // read() bor — yetarli
}

processInput(file);   // ishlaydi
processInput(stream); // ishlaydi
```

**3. Method Overloading (emulatsiya)** — JS da native yo'q:

```javascript
class Formatter {
  format(value) {
    if (typeof value === "number") return value.toFixed(2);
    if (typeof value === "string") return value.trim();
    if (Array.isArray(value)) return value.join(", ");
    return String(value);
  }
}
```

### Edge Cases
- **`super.method()`** — child override ichida parent implementation chaqirish; `[[HomeObject]]` internal slot orqali resolve qilinadi (statik dispatch, dynamic emas)
- **Polymorphism va `this` binding** — override method `this` ni dynamic ravishda resolve qiladi (late binding); `bind` bilan binding qotirilsa — polymorphism buziladi
- **`Symbol.iterator` polymorphism** — Array, Map, Set, String har biri o'z `[Symbol.iterator]` implementation'iga ega — `for...of` bir xil syntax bilan ishlaydi (parametric polymorphism)

### Follow-up savollar
1. **"Ad-hoc polymorphism vs parametric polymorphism?"** — Ad-hoc: bir nom, turli implementation (overloading); parametric: generic kod, har type uchun bir xil ishlaydi (TypeScript generics)
2. **"Polymorphism V8 performance'ga ta'sir qiladimi?"** — Ha, monomorphic call site (har doim bir xil shape) inline cache'da tez; polymorphic (2-4 shape) sekinroq; megamorphic (5+) generic slow path

</details>

### 5. SOLID printsiplaridan "S" va "O" ni tushuntiring [Middle]

<details>
<summary><strong>Javob</strong></summary>

**S — Single Responsibility Principle (SRP):** Har bir class bitta vazifa uchun javobgar. O'zgartirish uchun bitta sabab.

```javascript
// ❌ SRP buzilgan:
class UserService {
  createUser(data) { /* user yaratish */ }
  sendWelcomeEmail(user) { /* email */ }
  generateAvatar(user) { /* rasm */ }
  logAction(action) { /* log */ }
}

// ✅ SRP to'g'ri:
class UserService { createUser(data) { /* ... */ } }
class EmailService { send(to, template) { /* ... */ } }
class AvatarService { generate(user) { /* ... */ } }
class Logger { log(action) { /* ... */ } }
```

**O — Open/Closed Principle (OCP):** Kengaytirishga ochiq, o'zgartirishga yopiq.

```javascript
// ❌ OCP buzilgan — har yangi tur uchun if qo'shish kerak:
class Discount {
  calculate(type, price) {
    if (type === "student") return price * 0.8;
    if (type === "veteran") return price * 0.7;
    // yangi tur = kodni o'zgartirish ⚠️
  }
}

// ✅ OCP to'g'ri — yangi strategy qo'shish yetarli:
class StudentDiscount {
  calculate(price) { return price * 0.8; }
}
class VeteranDiscount {
  calculate(price) { return price * 0.7; }
}

class PriceCalculator {
  constructor(discountStrategy) {
    this.discount = discountStrategy;
  }
  getPrice(price) {
    return this.discount.calculate(price);
  }
}

// Yangi tur — faqat yangi class, mavjud kod o'zgarmaydi:
class EmployeeDiscount {
  calculate(price) { return price * 0.75; }
}
```

### Edge Cases
- **SRP "bitta sabab" formulasi** — Robert Martin: "Class faqat bitta actor (user role) uchun javobgar bo'lishi kerak" — `UserService` faqat user domain, lekin save/load/validate barchasi bir class'da OK
- **OCP modification'siz extension** — abstract'lar (interface, base class) orqali extend qilinadi; agar abstract noto'g'ri dizayn qilingan bo'lsa — refactor zarur (OCP "fundamentalist" emas)
- **Premature SRP** — 100 qatorlik class'ni 10 ta mikro-class'ga ajratish over-engineering; SRP'ni "bu class'ga o'zgarish kerak bo'lganda nima sabab keladi" savoli bilan baholash

### Follow-up savollar
1. **"SRP va Monolith Object farqi?"** — Monolith Object — bir class hamma narsani biladi (UserManager + EmailSender + Logger + DB); SRP'ni keskin buzadi
2. **"OCP Strategy Pattern bilan amalga oshadimi?"** — Ha, Strategy — OCP'ning klassik implementation'i; yangi behavior — yangi strategy class, mavjud kod o'zgarmaydi

</details>

### 6. Liskov Substitution Principle (LSP) nima? Buzilish misolini ko'rsating. [Middle+]

<details>
<summary><strong>Javob</strong></summary>

LSP: child class parent o'rnida ishlatilganda dastur **buzilmasligi** kerak. Ya'ni parent bilan ishlaydigan har qanday kod child bilan ham to'g'ri ishlashi shart.

```javascript
// ❌ LSP buzilgan — klassik Rectangle/Square muammosi:
class Rectangle {
  constructor(w, h) {
    this.width = w;
    this.height = h;
  }

  setWidth(w) { this.width = w; }
  setHeight(h) { this.height = h; }

  area() { return this.width * this.height; }
}

class Square extends Rectangle {
  setWidth(w) {
    this.width = w;
    this.height = w; // ❌ height ham o'zgaradi — kutilmagan!
  }
  setHeight(h) {
    this.width = h;  // ❌ width ham o'zgaradi
    this.height = h;
  }
}

// Bu funksiya Rectangle bilan to'g'ri ishlaydi:
function testArea(rect) {
  rect.setWidth(5);
  rect.setHeight(4);
  console.log(rect.area()); // 20 kutamiz
}

testArea(new Rectangle(0, 0)); // 20 ✅
testArea(new Square(0, 0));    // 16 ❌ — LSP buzildi!
// Square berilganda width = 4 (setHeight height bilan birga width'ni ham o'zgartirdi)


// ✅ LSP to'g'ri yechim:
class Shape {
  area() { throw new Error("implement qiling"); }
}

class Rectangle extends Shape {
  constructor(w, h) { super(); this.w = w; this.h = h; }
  area() { return this.w * this.h; }
}

class Square extends Shape {
  constructor(side) { super(); this.side = side; }
  area() { return this.side ** 2; }
}
// Endi ikkalasi ham Shape dan meros, bir-biriga bog'liq emas
```

### Edge Cases
- **Preconditions weakening** — child method parent'dan kamroq precondition talab qilishi mumkin (covariance OK), lekin ko'proq talab qilsa — LSP buziladi
- **Postconditions strengthening** — child parent'dan ko'proq guarantee berishi mumkin, lekin kamroq emas (kontrakt buzilmaydi)
- **Exception turi o'zgarishi** — child method parent'dan boshqa exception type tashlasa (`Penguin.fly() throw`), caller `try/catch` o'zgartirish kerak — LSP buziladi

### Follow-up savollar
1. **"LSP Java va JS'da farq qiladimi?"** — Konsept bir xil, lekin Java compile-time'da method signature tekshiriladi; JS runtime'da — duck typing tomonidan implicit kuzatiladi
2. **"LSP'ni TypeScript qanday yordam beradi?"** — Variance qoidalar (covariant return, contravariant params), interface enforcement; lekin behavior contract'ni hali ham developer kuzatishi kerak (compiler bilmaydi)

</details>

### 7. Composition vs Inheritance — qachon qaysi biri? [Middle]

<details>
<summary><strong>Javob</strong></summary>

| | **Inheritance** | **Composition** |
|---|---|---|
| **Munosabat** | "is-a" (It **is a** Hayvon) | "has-a" (Mashina **has** Motor) |
| **Bog'liqlik** | Tight coupling | Loose coupling |
| **Flexibility** | Kam — hierarxiya qotib qoladi | Yuqori — istalgan vaqtda o'zgaradi |
| **Qachon** | Aniq "is-a" bo'lganda, 2-3 daraja | Ko'pchilik holatda |

```javascript
// ❌ Inheritance xato ishlatilgan:
class Stack extends Array {
  peek() { return this.at(-1); }
}
const s = new Stack();
s.push(1, 2, 3);
s.shift();        // ❌ Stack da shift bo'lmasligi kerak!
s.splice(0, 1);   // ❌ Stack da splice bo'lmasligi kerak!
// Stack IS-A Array emas!

// ✅ Composition to'g'ri:
class Stack {
  #items = [];
  push(item)  { this.#items.push(item); }
  pop()       { return this.#items.pop(); }
  peek()      { return this.#items.at(-1); }
  get size()  { return this.#items.length; }
  // splice, shift, unshift — yo'q! Faqat stack operatsiyalari
}
```

**Qoida:** "Agar shubha bo'lsa — composition tanlang." Inheritance faqat aniq **is-a** munosabat bo'lganda va hierarxiya sayoz (2-3 daraja) bo'lganda.

### Edge Cases
- **Diamond problem yo'q** — JS'da multiple inheritance yo'q, lekin mixin chain'da bir xil method nomi konfliktda — oxirgi mixin ustun keladi (silent shadow)
- **`super` composition'da** — composition'da `super` yo'q; agar inner object method'i chaqirilishi kerak bo'lsa — explicit (`this.#engine.start()`)
- **Inheritance hierarchy refactoring qiyin** — 5 darajalik class chain'ni 1-2 ta darajaga qisqartirish — barcha subclass'lar buziladi; composition'da har dependency tashqaridan, refactor lokal

### Follow-up savollar
1. **"Composition over inheritance qoidasi qachondan?"** — GoF Design Patterns (1994); ko'p tilning hozirgi best practice (Go inheritance umuman yo'q)
2. **"Inheritance qachon zarur?"** — Framework callback'lari (React class component `extends Component`), DOM API (`extends HTMLElement` for custom elements), strict type hierarchy (Error subclass)

</details>

### 8. Duck typing nima va JS da qanday ishlatiladi? [Middle]

<details>
<summary><strong>Javob</strong></summary>

Duck typing — "Agar o'rdakdek yursa va o'rdakdek qaqillasa — u o'rdak." Ya'ni ob'ektning **type** i emas, **behavior** i (qanday method'lari bor) muhim.

JS dinamik tipli til bo'lgani uchun duck typing natural ishlaydi:

```javascript
// Iterator protocol — duck typing'ning klassik misoli:
// "Agar ob'ektda Symbol.iterator bor — u iterable"
const range = {
  from: 1,
  to: 5,
  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;
    return {
      next() {
        return current <= last
          ? { value: current++, done: false }
          : { done: true };
      }
    };
  }
};

for (const n of range) console.log(n); // 1, 2, 3, 4, 5
// range Array emas, Set emas — lekin iterable!

// Thenable — Promise.resolve duck typing ishlatadi:
const thenable = {
  then(resolve) { resolve(42); }
};
Promise.resolve(thenable).then(console.log); // 42
// Bu Promise emas, lekin then() bor — Promise dek ishlatildi!
```

**Afzalligi:** Interface'larsiz flexibility.
**Kamchiligi:** Compile-time xato yo'q — runtime da sinadi. TypeScript bu muammoni yechadi.

### Edge Cases
- **Partial duck** — ob'ekt method'ga ega lekin signature noto'g'ri (`source.read(extraArg)` kutilmagan parametr qabul qilmaydi) — runtime'da xato
- **Symbol-based protocol** — JS native protocol'lar `Symbol.iterator`, `Symbol.asyncIterator`, `Symbol.toPrimitive` — duck typing'ning standartlashtirilgan formasi
- **`in` operator vs `typeof`** — `"read" in source` — own + inherited property'larni tekshiradi; `typeof source.read === "function"` — qiymat callable ekanligini tekshiradi (xavfsizroq)

### Follow-up savollar
1. **"Duck typing nominal typing'dan qachon afzal?"** — Test'lar (mock object'lar nominal type talab qilmaydi), plugin architecture (uchinchi taraf kod sizning class'laringizdan meros olmasligi mumkin)
2. **"TypeScript structural typing duck typing'mi?"** — Ha, compile-time variant — TS type'lar shape bo'yicha mos kelishi yetarli (`implements` shart emas)

</details>

### 9. JS da abstract class qanday yaratiladi? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

JS da `abstract` keyword yo'q. Lekin `new.target` va `Error` throw qilish bilan emulatsiya qilish mumkin:

```javascript
class DataStore {
  constructor() {
    if (new.target === DataStore) {
      throw new Error("DataStore abstract — to'g'ridan yaratib bo'lmaydi");
    }
  }

  // Abstract method'lar — subclass implement qilishi SHART:
  save(key, value) {
    throw new Error(`${this.constructor.name}.save() implement qilinmagan`);
  }

  get(key) {
    throw new Error(`${this.constructor.name}.get() implement qilinmagan`);
  }

  // Concrete method — barcha subclass'larga umumiy:
  has(key) {
    return this.get(key) !== undefined;
  }
}

class MemoryStore extends DataStore {
  #data = new Map();
  save(key, value) { this.#data.set(key, value); }
  get(key) { return this.#data.get(key); }
}

class LocalStore extends DataStore {
  save(key, value) { localStorage.setItem(key, JSON.stringify(value)); }
  get(key) { return JSON.parse(localStorage.getItem(key)); }
}

// const ds = new DataStore();    // ❌ Error: abstract
const mem = new MemoryStore();    // ✅
mem.save("name", "Ali");
console.log(mem.has("name"));     // true — concrete method ishlaydi
```

`new.target` — constructor qaysi class uchun chaqirilganini ko'rsatadi. Agar `DataStore` o'zi uchun chaqirilsa — xato beradi.

### Edge Cases
- **`new.target` arrow function'da yo'q** — `() => new.target` `SyntaxError` (arrow function `[[Construct]]` yo'q)
- **`Reflect.construct(Base, args, NewTarget)`** — `new.target` ni manual set qilish; subclass simulation uchun (proxy yoki polyfill'da ishlatiladi)
- **Static method'lar abstract emas** — JS'da static method'ni abstract qilib bo'lmaydi to'g'ridan-to'g'ri; lekin constructor'da `if (typeof this.constructor.serialize !== "function") throw` orqali enforce qilinadi

### Follow-up savollar
1. **"TypeScript `abstract` keyword JS'da qanday compile bo'ladi?"** — `abstract` keyword runtime'da yo'qoladi; faqat compile-time tekshiruv (instantiate qilib bo'lmaydi)
2. **"Template Method pattern abstract method'lar bilan qanday ishlaydi?"** — Base class algoritm skeletini beradi (concrete method), subclass'lar abstract step'larni override qiladi — Hollywood Principle ("Don't call us, we'll call you")

</details>

### 10. SOLID ning "D" — Dependency Inversion qanday ishlaydi? JS misolida ko'rsating. [Senior]

<details>
<summary><strong>Javob</strong></summary>

DIP: Yuqori darajadagi modul pastki darajadagiga **bevosita bog'lanmasligi** kerak. Ikkalasi ham **abstraction**ga bog'lanishi kerak. JS da bu **dependency injection** orqali amalga oshiriladi:

```javascript
// ❌ DIP buzilgan — PaymentService to'g'ridan-to'g'ri Stripe ga bog'liq:
class PaymentService {
  constructor() {
    this.provider = new StripeProvider(); // qattiq bog'liqlik
  }
  charge(amount) {
    return this.provider.charge(amount);
  }
}
// PayPal ga o'tkazmoqchi bo'lsak — PaymentService kodini o'zgartirish kerak

// ✅ DIP to'g'ri — dependency injection:
// "Interface" (duck typing):
// Har qanday provider: { charge(amount), refund(id) }

class StripeProvider {
  charge(amount) { return `Stripe: $${amount} charged`; }
  refund(id) { return `Stripe: ${id} refunded`; }
}

class PayPalProvider {
  charge(amount) { return `PayPal: $${amount} charged`; }
  refund(id) { return `PayPal: ${id} refunded`; }
}

class PaymentService {
  constructor(provider) { // tashqaridan beriladi
    this.provider = provider;
  }
  charge(amount) { return this.provider.charge(amount); }
  refund(id) { return this.provider.refund(id); }
}

// Istalgan provider bilan ishlaydi — kodni o'zgartirmasdan:
const stripe = new PaymentService(new StripeProvider());
const paypal = new PaymentService(new PayPalProvider());

// Test uchun mock:
const mock = new PaymentService({ charge: () => "mock", refund: () => "mock" });
```

**DIP ning afzalligi:**
1. **Testability** — mock inject qilish oson
2. **Flexibility** — provider almashtirish bir qator
3. **Maintainability** — provider o'zgarganda PaymentService o'zgarmaydi

### Edge Cases
- **Circular dependency** — agar A B'ga, B A'ga bog'liq bo'lsa — DI container resolve qila olmaydi (yoki lazy proxy kerak)
- **Optional dependency** — ba'zi provider'lar majburiy emas (masalan, cache); constructor'da `?` (default null) yoki separate `setCache()` method ishlatiladi
- **Singleton vs transient** — bir provider instance barcha service'lar bo'lishi (singleton) yoki har chaqiruv yangi instance (transient) — lifecycle DI container responsibility

### Follow-up savollar
1. **"DI container nima?"** — Dependency Injection container — service registry; class'larni constructor argument'lari bilan avtomatik ulaydi (InversifyJS, tsyringe Node.js'da)
2. **"Service Locator vs Dependency Injection?"** — Service Locator pattern'da class o'zi container'dan dependency so'raydi (anti-pattern: hidden dependency); DI'da constructor argument explicit

<details>
<summary><strong>Deep Dive</strong></summary>

JavaScript da DIP static type system yo'qligi uchun **duck typing** orqali amalga oshiriladi — interface spec'da aniqlanmagan, lekin runtime'da `provider.charge` method mavjudligi tekshiriladi. TypeScript qo'shilganda `interface PaymentProvider { charge(amount: number): string }` kabi compile-time enforcement qo'shiladi. V8 nuqtai nazaridan, agar turli provider'lar bir xil method signature'ga ega bo'lsa — inline cache polymorphic holatda ishlaydi (2-4 ta shape), monomorphic IC'dan sekinroq. Hot path'da bitta provider type ishlatilganda IC monomorphic bo'ladi va TurboFan'da inline optimize qilinadi. Spec darajasida DI faqat composition pattern — `[[Construct]]` internal method argument'larni `this` ga assign qiladi, hech qanday "magic" yo'q.

### 11. Prototypal va classical OOP farqi nima? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

```javascript
// Classical OOP (Java, C#):
// Class = blueprint (shablon). Instance = nusxa.
// Class yaratilgandan keyin o'zgarmaydi.

// Prototypal OOP (JavaScript):
// Object = prototype (tirik ob'ekt). Instance = prototype dan meros.
// Istalgan vaqtda o'zgartirish mumkin.

const animal = {
  speak() { return `${this.name} gapirdi`; }

// Object.create — ob'ektdan ob'ektga bevosita meros:
const dog = Object.create(animal);
dog.name = "Rex";

console.log(dog.bark());  // "Hav!" — o'ziniki

// Classical OOP da bu MUMKIN EMAS
```

|---|---|---|

| **Runtime o'zgartirish** | Yo'q | Ha |
| **Abstract/Interface** | Til darajasida | Pattern bilan |

### Edge Cases
- **`__proto__` deprecated** — getter/setter sifatida hali ishlaydi, lekin `Object.getPrototypeOf` / `Object.setPrototypeOf` afzal (V8 `setPrototypeOf` Hidden Class'ni qayta hisoblaydi — sekin)

### Follow-up savollar
1. **"`Object.create(null)` qanday holatda foydali?"** — Dictionary/map (key'lar `__proto__`, `toString` kabi inherited property'lar bilan to'qnashmasin), prototype pollution xavfsizligi
2. **"`class` syntactic sugar deyish to'g'rimi?"** — Asosan ha, lekin ba'zi farqlar: `class` body strict mode default, hoisting yo'q, `new.target` mavjud, private fields faqat class'da ishlaydi

### 12. Mixin nima va nima uchun JS da ishlatiladi? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

Mixin — bir nechta manba'dan xatti-harakatlarni **aralashtirib olish** usuli. JS da multiple inheritance yo'q (`extends` faqat bitta class dan). Mixin bu muammoni yechadi:

```javascript
// Mixin'lar — funksiya sifatida:
const Serializable = (Base) => class extends Base {
  toJSON() {
    return JSON.stringify(this);
  }
  static fromJSON(json) {
    return Object.assign(new this(), JSON.parse(json));
  }
};

const Validatable = (Base) => class extends Base {
  validate() {
    for (const [key, value] of Object.entries(this)) {
      if (value === null || value === undefined) {
        throw new Error(`${key} bo'sh bo'lmasligi kerak`);
      }
    }
    return true;
  }
};

const Timestamped = (Base) => class extends Base {
  constructor(...args) {
    super(...args);
    this.createdAt = new Date();
    this.updatedAt = new Date();
  }
  touch() { this.updatedAt = new Date(); }
};

// Kerakli mixin'larni "aralashtirib" olish:
class User extends Timestamped(Validatable(Serializable(Object))) {
  constructor(name, email) {
    super();
    this.name = name;
    this.email = email;
  }
}

const user = new User("Ali", "ali@mail.com");
user.validate();           // ✅ Validatable dan
console.log(user.toJSON()); // Serializable dan
user.touch();              // Timestamped dan
```

**Prototype chain:** `user → User.prototype → Timestamped → Validatable → Serializable → Object.prototype`

### Edge Cases
- **Mixin'larni `Object.assign` bilan applylash** — instance'ga method'lar own property sifatida ko'chiriladi (prototype emas) — har instance'da memory takrorlanadi
- **Symbol method'lar mixin'da** — `[Symbol.iterator]` mixin orqali qo'shilsa, `for...of` darhol ishlaydi (Symbol property `Object.assign` orqali enumerable bo'lsa ko'chiriladi)
- **Mixin va `instanceof`** — `obj instanceof MixinClass` predictable emas (mixin har safar yangi class qaytaradi); structural check (`typeof obj.serialize === "function"`) afzal

### Follow-up savollar
1. **"Subclass factory mixin va `Object.assign` mixin orasidagi farq?"** — Factory: prototype chain (memory efficient, `super` ishlaydi); Object.assign: own property (har instance method copy, simple)
2. **"React class component'larda mixin nima uchun deprecated?"** — Multiple mixin'larda name conflict, complex inheritance, debugging qiyin — Hooks (composition) bilan almashtirildi

</details>

### 14. Delegation pattern nima va inheritance dan qanday farqi bor? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

Delegation — ob'ekt o'zi bajara olmaydigan ishni boshqa ob'ektga **topshiradi** (forward qiladi). Inheritance'dan farqi — bu "is-a" munosabat emas, balki "handles-by-forwarding".

```javascript
// Inheritance — Dog IS an Animal:
class Animal {
  eat() { return "yeyapman"; }
}
class Dog extends Animal {
  bark() { return "hav!"; }
}
// Dog.prototype.__proto__ === Animal.prototype
// Method Dog ichida — prototype chain orqali topiladi

// Delegation — UserService DELEGATES to Logger:
class Logger {
  log(msg) { console.log(`[LOG] ${msg}`); }
}

class UserService {
  #logger;
  constructor(logger) { this.#logger = logger; }

  createUser(name) {
    // O'zi log qilishni bilmaydi — Logger'ga TOPSHIRADI:
    this.#logger.log(`User yaratildi: ${name}`);
    return { name };
  }
}
```

| | Inheritance | Delegation |
|---|---|---|
| **Munosabat** | is-a | uses / forwards-to |
| **Bog'liqlik** | Qattiq (compile-time) | Sust (runtime o'zgaradi) |
| **Almashtirishlik** | Qiyin | Oson (dependency injection) |
| **JS'da** | `extends` / prototype | Forwarding / composition |

**OLOO (Kyle Simpson)** — JS prototypal delegation:

```javascript
const Validator = {
  validate() {
    return this.value != null && this.value !== "";
  }
};

const EmailField = Object.create(Validator);
EmailField.init = function(value) {
  this.value = value;
  return this;
};
EmailField.isValidEmail = function() {
  return this.validate() && this.value.includes("@");
};

const field = Object.create(EmailField).init("ali@mail.com");
console.log(field.isValidEmail()); // true
// field → EmailField → Validator — delegation chain
```

### Edge Cases
- **Forwarding boilerplate** — delegation har method uchun forwarding code talab qiladi (`this.#dependency.method()`); class'ga 10+ method delegation kerak bo'lsa — Proxy bilan auto-forward foydali
- **Inheritance vs delegation `this`** — inheritance'da `this` har doim subclass instance; delegation'da `this` "qaysi ob'ektdan chaqirildi" — masalan `Object.create(proto).method()`'da `this = obj`, `proto` emas
- **Composition + delegation kombinatsiya** — class composition'da inner object'ga delegate qiladi: `class A { #b = new B(); doX() { return this.#b.doX(); } }` — `A` `B`ning batafsil API'sini exposed qilmasdan reuse qiladi

### Follow-up savollar
1. **"Proxy bilan auto-delegation qanday qilinadi?"** — `new Proxy(target, { get: (t, p) => t.#dependency[p].bind(t.#dependency) })` — har property access dependency'ga forward
2. **"Decorator pattern delegation'ga asoslanganmi?"** — Ha, decorator inner object'ni o'rab oladi va method'larni forward qiladi (qo'shimcha behavior bilan)

### 15. Law of Demeter nima? Quyidagi kodda qanday buzilgan? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

Law of Demeter (LoD) — ob'ekt faqat **yaqin do'stlari** bilan gaplashishi kerak. "Begonalar" ning ichki tuzilishiga kirmaslik kerak. Yuqoridagi kodda `order → customer → address → city` — 3 daraja chuqur, bu **"train wreck"** deyiladi.

```javascript
// ❌ Muammo: address strukturasi o'zgarsa — SHU KOD SINADI
// Masalan: address → location ga qayta nomlansa, yoki address nested bo'lsa

// ✅ Law of Demeter — har bir ob'ekt o'z ma'lumotini o'zi beradi:
class Address {
  #city;
  constructor(city) { this.#city = city; }
  getCity() { return this.#city; }
}

class Customer {
  #address;
  #membership;
  constructor(address, membership) {
    this.#address = address;
    this.#membership = membership;
  }
  getCity() { return this.#address.getCity(); }    // delegatsiya
  isGold() { return this.#membership.tier === "gold"; } // delegatsiya
}

class Order {
  #customer;
  #total;
  constructor(customer, total) {
    this.#customer = customer;
    this.#total = total;
  }

  getShippingCity() {
    return this.#customer.getCity(); // faqat 1 daraja — yaqin do'st
  }

  applyDiscount() {
    if (this.#customer.isGold()) { // faqat 1 daraja
      this.#total *= 0.9;
    }
  }
}
```

**Qoida:** Agar method ichida 2+ ta dot (`.`) zanjiri boshqa ob'ektlarga kirayotgan bo'lsa — LoD buzilayotgan bo'lishi mumkin. (`builder.setA().setB()` bundan mustasno — bu method chaining, bitta ob'ekt.)

### Edge Cases
- **DTO (Data Transfer Object) bundan mustasno** — pure data ob'ektlari (`response.body.user.email`) odatda LoD qoidalariga kirmaydi; faqat behavior'li ob'ektlar tomon yo'naltirilgan
- **Property access chain** — `user.address?.city` — null-safe access; LoD'ni buzadi, lekin practical kod'da keng ishlatiladi (DTO holatida OK)
- **Wrapper anti-pattern** — har property uchun getter yaratish (`getCity`, `getStreet`, `getZip`) class API'sini bloat qiladi; balans muhim — faqat behavior darajasidagi delegation

### Follow-up savollar
1. **"LoD va Tell Don't Ask farqi?"** — LoD — kim bilan gaplash; Tell Don't Ask — qanday gaplash; LoD encapsulation, TDA behavior centralization
2. **"Fluent API LoD'ni buzadimi?"** — Yo'q, `query.where().select().limit()` har method `this` qaytaradi — bitta ob'ekt bilan ishlaymiz (method chaining, navigation emas)

### 16. Tell Don't Ask principle nima? Misol bilan tushuntiring. [Middle]

<details>
<summary><strong>Javob</strong></summary>

**Tell Don't Ask** — ob'ektdan ma'lumot so'ramang va uning o'rniga qaror qabul qilmang. Buning o'rniga ob'ektga nima qilish kerakligini **ayting** — u o'zi qaror qilsin.

```javascript
// ❌ Ask — so'rab, keyin tashqarida qaror qilish (procedural):
function shipOrder(order) {
  const status = order.getStatus();
  const items = order.getItems();
  if (status === "paid" && items.length > 0) {
    const weight = items.reduce((s, i) => s + i.weight, 0);
    if (weight > 30) {
      order.setShipping("freight");
    } else {
      order.setShipping("standard");
    }
    order.setStatus("shipped");
  }
}
// Business logika TASHQARIDA — Order o'zi haqida hech narsa bilmaydi

// ✅ Tell — ob'ektga aytish:
class Order {
  #status;
  #items;
  #shipping;

  ship() {
    if (this.#status !== "paid" || this.#items.length === 0) {
      throw new Error("Buyurtma jo'natishga tayyor emas");
    }
    this.#shipping = this.#totalWeight > 30 ? "freight" : "standard";
    this.#status = "shipped";
  }

  // Private getter (ES2022+) — private field + private method bilan birga qabul qilingan
  get #totalWeight() {
    return this.#items.reduce((s, i) => s + i.weight, 0);
  }
}

order.ship(); // ✅ Tell — nima qilishni aytdik, qanday qilishni Order o'zi biladi
```

**Afzalliklari:**
- Business logika **bitta joyda** — class ichida
- Encapsulation saqlanadi — ichki state tashqariga chiqmaydi
- Qaror logikasi takrorlanmaydi (DRY)

### Edge Cases
- **Read-only query istisno** — `cart.total`, `user.email` — qiymat olish OK (Tell strict emas), faqat decision-making + state change holatlarida Tell qoidasi
- **Tell return value** — operation muvaffaqiyat status'i qaytarish OK (`{ success: true }` yoki Result type), lekin internal state oshkor qilmaslik
- **External orchestration** — ba'zan workflow ko'p domain object'larga taalluqli (saga, transaction); bu holda command/event bus orqali — har object o'z domain'ini boshqaradi

### Follow-up savollar
1. **"Tell Don't Ask anemic domain model'ga qarshimi?"** — Ha, anemic model — class faqat getter/setter (data bag); Tell esa behavior'ni class ichiga joylashtirishni talab qiladi (rich domain model)
2. **"Validation Tell Don't Ask bilan qanday qo'llaniladi?"** — Validation method ichiga: `order.submit()` ichida `if (!this.canSubmit()) throw`; tashqaridan `if (order.canSubmit()) order.submit()` — ikki marta check (DRY buzilishi)

### 17. Coupling va Cohesion nima? Yaxshi dizayn qanday bo'ladi? [Middle]

<details>
<summary><strong>Javob</strong></summary>

**Coupling** — modullar o'rtasidagi bog'liqlik darajasi. **Cohesion** — modul ichidagi elementlarning bir-biriga aloqadorligi.

Yaxshi dizayn = **Loose Coupling** + **High Cohesion**.

```javascript
// ❌ Tight Coupling + Low Cohesion:
class UserManager {
  createUser(name) {
    const id = db.query("INSERT INTO users..."); // ❌ DB ga qattiq bog'liq
    smtp.send(`user-${id}@app.com`, "Welcome!"); // ❌ SMTP ga qattiq bog'liq
    redis.set(`session:${id}`, "{}");             // ❌ Redis ga qattiq bog'liq
    // Low cohesion: user + email + session = 3 xil soha
  }
}

// ✅ Loose Coupling + High Cohesion:
class UserService {
  // High cohesion: faqat user operatsiyalari
  #repo; #events;

  constructor(repo, events) { // Loose coupling: dependency injection
    this.#repo = repo;
    this.#events = events;
  }

  createUser(name) {
    const user = this.#repo.save({ name });
    this.#events.emit("user:created", user); // qolganlari event handler qiladi
    return user;
  }
}
```

| | Yomon | Yaxshi |
|---|---|---|
| **Coupling** | Tight — to'g'ridan-to'g'ri `new`, global, ichki field | Loose — interface, DI, events |
| **Cohesion** | Low — aralash vazifalar bir class da | High — bir soha, bir class |

### Edge Cases
- **Afferent vs efferent coupling** — afferent (kim sizga bog'liq), efferent (siz kimga bog'liqsiz) — Instability metric: `I = Ce / (Ca + Ce)`; abstract module Ca > Ce, concrete Ce > Ca
- **Temporal coupling** — method'lar bir tartibda chaqirilishi shart (`init` → `start` → `stop`); state machine bilan explicit qilish kerak
- **Connascence** — coupling'ning batafsil klassifikatsiyasi (name, type, meaning, position, algorithm) — Meilir Page-Jones tomonidan kiritilgan

### Follow-up savollar
1. **"Module level vs class level coupling?"** — Module: import dependencies (`import x from "y"`); class: composition, inheritance — class darajasidagi loose coupling DI bilan, module darajasidagi facade/adapter bilan
2. **"High cohesion'ga LCOM metric qanday yordam beradi?"** — Lack of Cohesion of Methods — qaysi method'lar bir xil field'larni ishlatadi; LCOM yuqori bo'lsa — class ikkiga bo'linadi (refactor signali)

### 18. Symbol.hasInstance qanday ishlaydi? Custom instanceof yozing. [Senior]

<details>
<summary><strong>Javob</strong></summary>

`instanceof` operator ichida `Symbol.hasInstance` static method chaqiriladi. Uni override qilib, `instanceof` xatti-harakatini butunlay o'zgartirish mumkin:

```javascript
// ✅ Interface tekshiruvchi — duck typing bilan birga:
class Stringable {
  static [Symbol.hasInstance](instance) {
    return instance != null && typeof instance.toString === "function"
      && instance.toString !== Object.prototype.toString;
  }
}

class User {
  constructor(name) { this.name = name; }
  toString() { return `User: ${this.name}`; }
}

console.log(new User("Ali") instanceof Stringable); // true — custom toString bor
console.log("hello" instanceof Stringable);          // true — String.toString
console.log({} instanceof Stringable);               // false — default toString
console.log(42 instanceof Stringable);               // true — Number.prototype.toString !== Object.prototype.toString

// ✅ Array-like tekshirish:
class ArrayLike {
  static [Symbol.hasInstance](instance) {
    return instance != null
      && typeof instance.length === "number"
      && Number.isInteger(instance.length)
      && instance.length >= 0;
  }
}

console.log([1, 2] instanceof ArrayLike);       // true
console.log("hello" instanceof ArrayLike);      // true (length = 5)
console.log({ length: 3 } instanceof ArrayLike); // true
console.log({ length: -1 } instanceof ArrayLike); // false
```

**Under the hood:** `x instanceof Foo` → engine `Foo[Symbol.hasInstance](x)` ni chaqiradi. Default implementation prototype chain bo'ylab yuradi, lekin static method bilan butunlay o'zgartirishingiz mumkin.

### Edge Cases
- **`Symbol.hasInstance` non-writable** — `Function.prototype[Symbol.hasInstance]` `configurable: false, writable: false` — uni o'zgartirib bo'lmaydi, lekin subclass'da yangi static method e'lon qilish mumkin
- **Primitive'lar bilan `instanceof`** — `5 instanceof Number` `false`, lekin `Number[Symbol.hasInstance](5)` orqali custom logic yozish mumkin (autoboxing tekshiruvi)
- **`null`/`undefined`** — custom `[Symbol.hasInstance]` ichida `instance != null` tekshiruvi shart, aks holda `TypeError` (cannot read property of null)

### Follow-up savollar
1. **"`instanceof` cross-realm muammosi nima?"** — Har iframe/worker o'z `Array.prototype`'iga ega; `arr instanceof Array` boshqa realm'dan kelgan array uchun `false` qaytaradi — `Array.isArray(arr)` ishlatish kerak
2. **"`Symbol.hasInstance` override'i havfsizmi?"** — Yo'q, bu library code uchun confusing — `instanceof` kutilmagan natija qaytarishi mumkin; namespace conflict oldini olish uchun explicit method (`isAssignable`) afzal

<details>
<summary><strong>Deep Dive</strong></summary>

Spec'da `instanceof` operatori `InstanceofOperator(V, target)` abstract operation'ni chaqiradi. Birinchi qadam: `target[@@hasInstance]` bor-yo'qligini tekshiradi (`GetMethod`). Agar bor — uni chaqiradi va natijani `ToBoolean` qiladi. Agar yo'q — `OrdinaryHasInstance(target, V)` chaqiriladi, bu prototype chain bo'ylab yuradi (`[[Prototype]]` slot orqali). `Function.prototype[@@hasInstance]` default implementation sifatida barcha funksiyalarda mavjud va `OrdinaryHasInstance` ni chaqiradi. `target[@@hasInstance]` callable bo'lishi shart — aks holda `TypeError`. V8 inline cache `instanceof` operatorini optimize qiladi: agar bitta constructor (masalan `User`) monomorphic ishlatilsa (har doim bir xil constructor) — IC default `OrdinaryHasInstance` path'ni inline qiladi.

</details>

</details>

### 19. Proxy bilan OOP encapsulation/validation qanday qilinadi? [Senior]

<details>
<summary><strong>Javob</strong></summary>

Proxy ob'ektning fundamental operatsiyalarini (get, set, delete) tutib oladi. Bu OOP da runtime validation, access control va observable pattern'ni amalga oshiradi:

```javascript
// ✅ Typed object — runtime type enforcement:
function createTyped(schema) {
  return new Proxy({}, {
    set(target, prop, value) {
      if (!(prop in schema)) {
        throw new Error(`Noma'lum property: ${prop}`);
      }
      const expectedType = schema[prop];
      if (typeof value !== expectedType) {
        throw new TypeError(
          `${prop}: ${expectedType} kutildi, ${typeof value} berildi`
        );
      }
      target[prop] = value;
      return true;
    }
  });
}

const user = createTyped({
  name: "string",
  age: "number",
  active: "boolean"
});

user.name = "Ali";       // ✅
user.age = 25;           // ✅
// user.age = "yigirma"; // ❌ TypeError
// user.role = "admin";  // ❌ Error: noma'lum property
```

**Proxy afzalliklari OOP da:**
- **Runtime validation** — compile-time emas, amalda ishlaydi
- **Transparent** — client kodi o'zgarmaydi, proxy "yashirin"
- **Flexible** — istalgan vaqtda qoidalar o'zgaradi
- **Cross-cutting concerns** — logging, caching, access control

### Edge Cases
- **Proxy invariants** — agar target'da `configurable: false, writable: false` property bo'lsa, `get` trap boshqa qiymat qaytarsa engine `TypeError` tashlaydi (spec invariant buzilganini aniqlaydi)
- **`this` binding** — proxy method'lari ichida `this` proxy bo'ladi, target emas; agar method ichida private field ishlatilsa (`#data`), Proxy orqali kirish `TypeError` beradi (private fields proxy'ga "ko'rinmaydi")
- **`Reflect` bilan to'liq forwarding** — `Reflect.set(target, prop, value)` har doim spec'ga muvofiq operatsiyani bajaradi, manual `target[prop] = value` ba'zi edge case'larda farq qiladi (masalan, setter inheritance bilan)

### Follow-up savollar
1. **"Proxy bilan private field'ni intercept qilish mumkinmi?"** — Yo'q. `#field` spec'da ob'ektning `[[PrivateElements]]` internal slot'ida saqlanadi (PrivateName kalit bilan), oddiy property emas — shuning uchun Proxy `[[Get]]`/`[[Set]]` trap'lariga umuman kirmaydi. ### 3. EventEmitter'ni OOP printsiplari bilan implement qiling [Senior]

**Savol:** EventEmitter class yarating — `on`, `off`, `emit`, `once` method'lari bilan. Encapsulation va polymorphism ishlating.

<details>
<summary><strong>Javob</strong></summary>

```javascript
class EventEmitter {
  #listeners = new Map();

  on(event, callback) {
    if (!this.#listeners.has(event)) {
      this.#listeners.set(event, []);
    }
    this.#listeners.get(event).push(callback);
    return this; // chaining uchun
  }

  off(event, callback) {
    const callbacks = this.#listeners.get(event);
    if (!callbacks) return this;
    const index = callbacks.indexOf(callback);
    if (index !== -1) callbacks.splice(index, 1);
    return this;
  }

  emit(event, ...args) {
    const callbacks = this.#listeners.get(event);
    if (!callbacks) return false;
    for (const cb of [...callbacks]) { // copy — once o'chirish xavfsiz
      cb.apply(this, args);
    }
    return true;
  }

  once(event, callback) {
    const wrapper = (...args) => {
      this.off(event, wrapper);
      callback.apply(this, args);
    };
    return this.on(event, wrapper);
  }
}

// Test:
const emitter = new EventEmitter();
const handler = (msg) => console.log(`Got: ${msg}`);

emitter.on("data", handler);
emitter.once("connect", () => console.log("Connected!"));

emitter.emit("connect"); // "Connected!"
emitter.emit("connect"); // (hech narsa — once!)
emitter.emit("data", "hello"); // "Got: hello"

emitter.off("data", handler);
emitter.emit("data", "world"); // (hech narsa — off qilindi)
```

**OOP printsiplari:**
- **Encapsulation:** `#listeners` private — tashqaridan manipulate qilib bo'lmaydi
- **Polymorphism:** `once` ichida `on` va `off` ni qayta ishlatadi
- **SRP:** Faqat event boshqarish — boshqa vazifa yo'q

### Edge Cases
- **Emit ichida off** — listener `emit` paytida o'zini `off` qilsa, iteration buzilmasligi uchun `[...callbacks]` copy ishlatildi
- **Async listener'lar** — `emit` synchronous; async callback'da xato bo'lsa `unhandledRejection` (uni catch qilish handler responsibility'si)
- **Memory leak** — listener'ni `off` qilmasdan instance'ni tashlab yuborilsa, callback'lar GC tomonidan tozalanmaydi (closure reference saqlanadi)

### Follow-up savollar
1. **"`on` o'rniga `addEventListener` ishlatsangiz farqi nima?"** — DOM EventTarget'da `addEventListener` capture/bubble phase, `passive`, `once` option'lari bor; Node.js EventEmitter sodda — faqat listener queue
2. **"`emit` async qilish kerakmi?"** — Ko'pchilik hollarda yo'q (event handler tartibi muhim); lekin `queueMicrotask`/`setImmediate` bilan emit defer qilinishi mumkin (handler exception emit caller'ga tushmasligi uchun)

### 4. Method Chaining (Fluent Interface) nima? Implement qiling. [Middle]

<details>
<summary><strong>Javob</strong></summary>

Method chaining — har bir method `this` ni qaytaradi, shunda bir necha method'ni zanjir shaklida chaqirish mumkin. Bu pattern jQuery, Lodash, Express, va ko'plab JS kutubxonalarida ishlatiladi.

```javascript
class FormValidator {
  #rules = {};
  #errors = [];
  #data;

  setData(data) {
    this.#data = data;
    this.#errors = [];
    return this; // ← this qaytarish = chaining mumkin
  }

  required(field) {
    if (!this.#data[field]) {
      this.#errors.push(`${field} majburiy`);
    }
    return this;
  }

  minLength(field, min) {
    if (this.#data[field]?.length < min) {
      this.#errors.push(`${field} kamida ${min} ta belgi`);
    }
    return this;
  }

  isEmail(field) {
    if (this.#data[field] && !this.#data[field].includes("@")) {
      this.#errors.push(`${field} noto'g'ri email`);
    }
    return this;
  }

  validate() {
    return {
      isValid: this.#errors.length === 0,
      errors: [...this.#errors]
    };
  }
}

// Fluent interface — zanjir:
const result = new FormValidator()
  .setData({ name: "Al", email: "invalid", age: "" })
  .required("name")
  .minLength("name", 3)
  .required("email")
  .isEmail("email")
  .required("age")
  .validate();

console.log(result);
// { isValid: false, errors: ["name kamida 3 ta belgi", "email noto'g'ri email", "age majburiy"] }
```

**Muhim:** `return this` — mutable chaining (original o'zgaradi). Immutable chaining uchun `return new ClassName(...)` ishlatiladi (masalan, `Array.map()`, `String.trim()`).

### Edge Cases
- **`this` lost** — agar method `bind` qilinmasdan callback'ga uzatilsa, `this` undefined bo'lishi mumkin (strict mode) — chaining buziladi
- **Async chaining** — async method'lar Promise qaytaradi, `this` emas — chain uzilishi; resolution: `return this.promise = promise.then(...)` pattern yoki async builder
- **Subclass chaining** — `class Extended extends FormValidator { extraRule() {...} }` — parent method `return this` qaytarsa, `Extended` instance bo'ladi (correct chaining)

### Follow-up savollar
1. **"Builder pattern method chaining bilan birxilmi?"** — Builder ko'pincha chaining ishlatadi, lekin builder odatda `build()` orqali immutable result qaytaradi; chaining faqat syntax
2. **"Fluent interface'da xato qanday boshqariladi?"** — Errors'ni internal array'da to'plash (lazy) yoki har method'da throw (eager); ko'pincha lazy — `.validate()` chaqirilganda error list qaytadi

### 5. ISP (Interface Segregation) JS'da `interface` keyword yo'qligida qanday qo'llaniladi? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

ISP — "Client'lar o'ziga kerak bo'lmagan method'larga bog'lanmasligi kerak". JS'da `interface` keyword yo'q (TypeScript'da bor), shu sababli ISP **composition** va **mixin** pattern'lari orqali qo'llaniladi.

```javascript
// ❌ ISP buzilgan — "fat interface":
class MultifunctionPrinter {
  print(doc) { /* ... */ }
  scan(doc) { /* ... */ }
  fax(doc) { /* ... */ }
  staple(docs) { /* ... */ }

// Oddiy printer fax va staple ni implement qila olmaydi:
class CheapPrinter extends MultifunctionPrinter {

  staple() { throw new Error("Not supported"); } // ❌
```

- **Method nom konflikti** — ikki mixin bir xil method nomiga ega bo'lsa, oxirgi qo'shilgan oldingisini override qiladi (silent overshadow)

<summary><strong>Deep Dive</strong></summary>

V8 nuqtai nazaridan, factory mixin pattern har instance uchun yangi prototype chain hosil qilmaydi — agar `CanPrint(Object)` ko'p marta chaqirilsa har safar yangi class object yaratiladi (memoization usuli ishlatilsa cache qilish mumkin).

### 6. OLOO (Objects Linking to Other Objects) pattern nima va class'dan qanday farqi bor? [Senior]

<details>
<summary><strong>Javob</strong></summary>

OLOO — Kyle Simpson tomonidan kiritilgan pattern. Class hierarchy o'rniga **ob'ektlarni bevosita bog'lash** — `Object.create()` orqali delegation chain quriladi. Class abstraction'ni tashlab, prototypal nature'ni to'liq foydalanadi.

```javascript
// Class-based — sinthetic "is-a" hierarchy:
class Task {
  constructor(label) { this.label = label; }
  describe() { return `Task: ${this.label}`; }
}

class UrgentTask extends Task {
  constructor(label) {
    super(label);
    this.urgent = true;
  }
  describe() { return `URGENT: ${this.label}`; }
}

const t = new UrgentTask("Deploy");
// t → UrgentTask.prototype → Task.prototype → Object.prototype

// OLOO — class'siz, oddiy ob'ektlar:
const Task = {
  init(label) {
    this.label = label;
    return this; // chaining
  },
  describe() {
    return `Task: ${this.label}`;
  }
};

const UrgentTask = Object.create(Task);
UrgentTask.initUrgent = function(label) {
  this.init(label);     // parent'ga delegate
  this.urgent = true;
  return this;
};
UrgentTask.describe = function() {
  return `URGENT: ${this.label}`;
};

const task = Object.create(UrgentTask).initUrgent("Deploy");
console.log(task.describe()); // "URGENT: Deploy"
// task → UrgentTask → Task → Object.prototype (bir xil chain!)
```

| Xususiyat | Class | OLOO |
|-----------|-------|------|
| **Syntax** | `class`/`extends` | `Object.create` |
| **Konsept** | "instantiation" | "delegation" |
| **`new` keyword** | Majburiy | Yo'q |
| **`this`** | constructor da binding | call site'da |
| **Prototype chain** | Implicit | Explicit |
| **TC39 status** | Standard syntax | Plain object pattern |

**OLOO afzalliklari:**
- **Sodda mental model** — class abstraction yo'q, faqat ob'ektlar va delegation
- **Constructor "magic" yo'q** — `new` keraksiz, `this` yo'qolishi muammosi kamroq
- **Runtime flexibility** — chain'ni istalgan vaqtda o'zgartirish mumkin

**Kamchiliklari:**
- **Tool support kam** — class IDE, debugger, TypeScript bilan yaxshi integration
- **`instanceof` ishlamaydi** — chunki constructor yo'q
- **Konvensiya emas** — communityda kam tarqalgan, jamoa ishi qiyinroq

### Edge Cases
- **`Object.create(null)`** — `[[Prototype]]` null bo'lgan ob'ekt; `toString`, `hasOwnProperty` ham yo'q (pure dictionary, prototype pollution'dan himoya)
- **Property shadow** — `UrgentTask.describe` `Task.describe` ni override qiladi, lekin `Task.describe` chain'da hali ham mavjud (`Object.getPrototypeOf(UrgentTask).describe`)
- **`this` chain'da delegation** — `task.describe()` chaqirilganda `this = task` bo'ladi, prototype'da topilgan method ham `task` ustida ishlaydi (dynamic dispatch)

### Follow-up savollar
1. **"`Object.create` va `new` farqi nima?"** — `new Foo()` constructor'ni chaqiradi, prototype'ni `Foo.prototype`'ga set qiladi; `Object.create(proto)` faqat prototype'ni set qiladi, constructor yo'q
2. **"OLOO'da private state qanday saqlanadi?"** — `WeakMap` orqali (private fields class'ga bog'langan, plain object'da ishlamaydi); yoki closure ichida factory function bilan

<details>
<summary><strong>Deep Dive</strong></summary>

OLOO va class texnik jihatdan **bir xil prototype delegation mexanizmi** orqali ishlaydi — farq faqat syntax va konseptda. `Object.create(proto)` spec'da `OrdinaryObjectCreate(proto)` ni chaqiradi — yangi ob'ekt yaratib `[[Prototype]]` slot'ini set qiladi. `class Child extends Parent` ClassDefinitionEvaluation paytida `Child.prototype`ning `[[Prototype]]`sini `Parent.prototype`ga, `Child` constructor'ning `[[Prototype]]`sini esa `Parent` constructor'ga ulaydi. Derived constructor'da `super()` chaqirilganda parent constructor `GetSuperConstructor` orqali — running constructor'ning `[[Prototype]]`sini o'qib topiladi (`[[HomeObject]]` emas; u faqat `super.method()` property access uchun). V8 nuqtai nazaridan ikkalasi ham bir xil Hidden Class transition chain'ni hosil qiladi — performance farqi yo'q. Kyle Simpson'ning argumenti: class mental model — Java/C# tushunchasini JavaScript'ga keltiradi, lekin JS prototypal — class abstraction noto'g'ri mental model. Amaliyotda class syntax community tomonidan qabul qilingan va ekosistema (TypeScript, IDE, framework'lar) class'ga moslashtirilgan. OLOO niche pattern — kichik kod base yoki ta'lim maqsadida foydali, lekin production scale loyihalarda class afzal.

</details>

</details>

### 7. CQRS (Command Query Responsibility Segregation) Tell Don't Ask bilan qanday bog'liq? [Senior]

<details>
<summary><strong>Javob</strong></summary>

**CQRS** — operatsiyalarni ikkiga ajratish: **Command** (state o'zgartiradi, qiymat qaytarmaydi) va **Query** (qiymat o'qiydi, state o'zgartirmaydi). Tell Don't Ask faqat **Command** uchun strict — Query uchun esa "ask" normal va kerakli.

```javascript
// CQRS-aware OOP design:
class ShoppingCart {
  #items = [];
  #discountCode = null;

  // ─── Commands — Tell pattern (state o'zgartiradi) ───
  addItem(product, quantity = 1) {
    this.#items.push({ product, quantity });
    // void — qiymat qaytarmaydi
  }

  removeItem(productId) {
    this.#items = this.#items.filter(i => i.product.id !== productId);
  }

  applyDiscount(code) {
    if (!this.#isValidCode(code)) {
      throw new Error("Invalid discount code");
    }
    this.#discountCode = code;
  }

  clear() {
    this.#items = [];
    this.#discountCode = null;
  }

  // ─── Queries — Ask pattern (read-only) ───
  get isEmpty() { return this.#items.length === 0; }
  get itemCount() { return this.#items.length; }
  get subtotal() {
    return this.#items.reduce((s, i) => s + i.product.price * i.quantity, 0);
  }
  get total() {
    const discount = this.#discountCode ? this.subtotal * 0.1 : 0;
    return this.subtotal - discount;
  }

  // ─── Private helper (neither command nor query externally) ───
  #isValidCode(code) {
    return ["SUMMER10", "WELCOME10"].includes(code);
  }
}

const cart = new ShoppingCart();

// Commands — Tell:
cart.addItem({ id: 1, name: "Laptop", price: 1500 });
cart.addItem({ id: 2, name: "Mouse", price: 25 }, 2);
cart.applyDiscount("SUMMER10");

// Queries — Ask:
console.log(cart.itemCount); // 2
console.log(cart.subtotal);  // 1550
console.log(cart.total);     // 1395 (10% off)
```

**Tell Don't Ask + CQRS qoidasi:**

| Operatsiya turi | Pattern | Misol |
|----------------|---------|-------|
| **State o'zgartirish** | Tell | `cart.applyDiscount("X")` |
| **Decision-making (with state change)** | Tell | `account.withdraw(100)` |
| **Read-only data** | Ask OK | `cart.total`, `user.email` |
| **Computed property** | Ask OK | `order.isShippable` |
| **External filtering** | Ask + external logic | `users.filter(u => u.isActive)` |

**Anti-pattern:** Combined operations buzadi:

```javascript
// ❌ Anti-pattern — command + query bir method'da:
class Stack {
  pop() {
    return this.#items.pop(); // state o'zgartiradi VA qiymat qaytaradi
  }
}
// Bu klassik anti-pattern — lekin amalda accepted (LIFO semantics)

// ✅ Toza CQRS:
class StrictStack {
  peek() { return this.#items[this.#items.length - 1]; } // Query
  remove() { this.#items.pop(); }                          // Command (void)
}
```

### Edge Cases
- **Command'da return qiymat** — strict CQRS'da `void`; lekin DDD'da Command ID yoki Result type qaytarish OK (async operation tracking uchun)
- **Query'da caching** — qaytarilgan ob'ekt mutable bo'lsa, caller uni o'zgartirsa internal state'ga ta'sir qiladi (frozen copy yoki defensive clone kerak)
- **Event-driven Command** — Command method'i state o'zgartirish o'rniga event emit qilishi mumkin (Event Sourcing); state event handler tomonidan o'zgartiriladi

### Follow-up savollar
1. **"Event Sourcing CQRS bilan bog'liqligi?"** — CQRS Command'lari state o'zgarish o'rniga immutable event'lar yozadi; current state event'lardan replay qilinadi (audit log, time-travel debugging)
2. **"Query'da computed property cache qilish kerakmi?"** — Murakkab hisob (O(n²) yoki tashqi I/O) bo'lsa — ha (memoization); oddiy hisob — invalidation overhead foydadan kop bo'lishi mumkin

<details>
<summary><strong>Deep Dive</strong></summary>

CQRS architecture darajasida ham qo'llaniladi — Event Sourcing va microservices'da Command Bus va Query Bus alohida bo'ladi. CQRS Tell Don't Ask bilan birlashganda **business logic**'ni domain object ichida saqlash printsipi mustahkamlanadi. Bu pattern Domain-Driven Design (DDD)'da markaziy — Aggregate Root command'larni handle qiladi va internal invariant'larini saqlaydi, query'lar esa optimized read model orqali ishlaydi. JavaScript da CQRS oddiy qoida sifatida class darajasida ham qo'llanilishi mumkin — Tell uchun void method'lar, Query uchun getter va read-only method'lar. Production microservices'da Command Bus odatda async queue (RabbitMQ, Kafka) orqali ishlaydi — Command yuborish va uning amalga oshirilishi orasida eventually consistent gap mavjud, Query esa denormalized read database'dan o'qiydi (CAP theorem trade-off).

</details>

</details>

### 8. Method overloading JS da nima uchun yo'q va qanday emulatsiya qilinadi? [Middle+]

<details>
<summary><strong>Javob</strong></summary>

Method overloading — bir xil nomli, lekin **turli signature**li method'lar (Java/C#'da bor: `add(int, int)` va `add(string, string)` alohida method'lar). JavaScript'da overloading **yo'q** — bir nom bilan ikkinchi method e'lon qilinsa, birinchini override qiladi.

```javascript
// ❌ Java/C# da bo'ladigan — JS da YO'Q:
class Calculator {
  add(a, b) { return a + b; }
  add(a, b, c) { return a + b + c; } // override qilinadi — birinchi method o'chadi!
}

const calc = new Calculator();
console.log(calc.add(1, 2));    // NaN — chunki c = undefined, 1+2+undefined = NaN
console.log(calc.add(1, 2, 3)); // 6
```

**Nima uchun yo'q:** JavaScript dynamic typed va engine compile-time'da argument type'larini bilmaydi. Class body'da har method o'z nomi (key) sifatida prototype'ga `DefineMethodProperty` (spec operation, `[[DefineOwnProperty]]` ustida) orqali qo'shiladi — bir xil nom ikkinchi qo'shilganda birinchisini override qiladi.

**Emulatsiya usullari:**

```javascript
// 1. arguments/rest parameter va typeof tekshirish:
class Logger {
  log(...args) {
    if (args.length === 1) {
      const [val] = args;
      if (typeof val === "string") return `[INFO] ${val}`;
      if (val instanceof Error) return `[ERROR] ${val.message}`;
      if (typeof val === "object") return `[DATA] ${JSON.stringify(val)}`;
    }
    if (args.length === 2) {
      const [level, msg] = args;
      return `[${level.toUpperCase()}] ${msg}`;
    }
    throw new TypeError("Invalid arguments");
  }
}

const l = new Logger();
console.log(l.log("Hello"));                // "[INFO] Hello"
console.log(l.log(new Error("Failed")));    // "[ERROR] Failed"
console.log(l.log({ user: "Ali" }));        // '[DATA] {"user":"Ali"}'
console.log(l.log("warn", "Slow query"));   // "[WARN] Slow query"

// 2. Options object pattern (preferred — explicit):
class HttpClient {
  request(options) {
    const {
      method = "GET",
      url,
      body = null,
      headers = {},
      timeout = 5000
    } = options;
    // ... use parameters
    return { method, url, body, headers, timeout };
  }
}

const client = new HttpClient();
client.request({ url: "/api/users" });
client.request({ method: "POST", url: "/api/users", body: { name: "Ali" } });

// 3. Function dispatching:
class ShapeFactory {
  create(type, ...args) {
    const factories = {
      circle: (r) => ({ type: "circle", area: Math.PI * r ** 2 }),
      square: (s) => ({ type: "square", area: s ** 2 }),
      rectangle: (w, h) => ({ type: "rectangle", area: w * h })
    };
    const factory = factories[type];
    if (!factory) throw new Error(`Unknown shape: ${type}`);
    return factory(...args);
  }
}

const factory = new ShapeFactory();
console.log(factory.create("circle", 5));    // { type: "circle", area: 78.539... }
console.log(factory.create("rectangle", 4, 6)); // { type: "rectangle", area: 24 }
```

**TypeScript bilan compile-time overload:**

```typescript
class Database {
  // Overload signatures (compile-time only):
  query(sql: string): Promise<unknown[]>;
  query(sql: string, params: unknown[]): Promise<unknown[]>;
  query(table: string, conditions: object): Promise<unknown[]>;

  // Implementation (single function):
  query(sqlOrTable: string, paramsOrConditions?: unknown[] | object): Promise<unknown[]> {
    // runtime dispatch logic
    return Promise.resolve([]);
  }
}
```

### Edge Cases
- **`typeof null === "object"`** — dispatch logic'da `null` check'ni `typeof` dan oldin qilish kerak (`val === null` birinchi)
- **`Array.isArray` vs `instanceof Array`** — cross-realm code'da (iframe, worker) `Array.isArray` ishonchli, `instanceof` esa false-negative qaytarishi mumkin
- **Optional parameter va `undefined`** — `add(1, 2)` chaqirilganda `c = undefined`, dispatch logic'da `arguments.length` ishlatish kerak (`undefined` value vs not passed farqi)

### Follow-up savollar
1. **"TypeScript overload signature runtime'da bormi?"** — Yo'q, compile'da o'chiriladi; type check faqat IDE/compiler darajasida
2. **"`function.length` overloading'ga ta'sir qiladimi?"** — `function.length` faqat birinchi rest/default'gacha bo'lgan parametr sonini qaytaradi; dispatch logic uchun `arguments.length` (regular function) yoki `args.length` (rest) ishlatiladi

<details>
<summary><strong>Deep Dive</strong></summary>

V8 nuqtai nazaridan, overloading emulation pattern'i monomorphic dispatch'dan ko'ra polymorphic'ga moyil bo'ladi — chunki `args.length` va `typeof` check'lar har chaqiruvda turli branch'larga olib boradi. IC megamorphic holatga o'tishi mumkin agar method ko'p xil argument type kombinatsiyalari bilan chaqirilsa. Performance-critical kod uchun **alohida method'lar** (`logInfo`, `logError`, `logData`) overloading emulation'dan tezroq — har biri monomorphic IC entry'ga ega bo'ladi. Options object pattern (named arguments) explicit va o'qish oson, lekin destructuring overhead qo'shadi — V8 odatda buni inline qiladi, lekin object yaratish heap allocation talab qiladi (escape analysis bilan optimize bo'lishi mumkin, agar object function'dan tashqariga "escape" qilmasa). Spec darajasida `Function.prototype` faqat bitta `[[Call]]` internal method'ga ega — har key bir function'ga point qiladi, bir nom bilan ikkinchi method e'lon qilinsa `[[DefineOwnProperty]]` orqali oldingisi override qilinadi (`writable: true` default sababli).
